### Task 10 final-review follow-up (human-approved)
- Stuck startup: on `CoreEvent::Error` while Busy and not logged in (restore or login in flight; the engine's `restore()` emits `Error`, not `NoSession`, for an unavailable keychain, an inconsistent or unparsable record, a missing store dir, or a failed `restore_session`) the CLI now prints the error, a fixed hint, and returns to Idle, so stdin is read and `/login` and `/quit` work. Other not-logged-in exits from Busy were checked: `LoginFailed`, `NoSession` (goes to the username prompt), `SessionExpired`, `LoggedOut` already leave Busy. While a login or restore is genuinely in flight the CLI still does not read stdin (so piped input queued behind it is not lost); a hung login can only be left with Ctrl-C.

While a hidden password read (`rpassword`) is pending, Ctrl-C is deferred (`ctrl_c_action`, `Cli::interrupt_action`): the CLI prints a note, the read finishes on Enter (rpassword restores echo), the password is dropped, and the CLI exits through the normal shutdown path. With `--password-stdin` no echo is involved, so Ctrl-C quits at once. No new dependency. Tests: `ctrl_c_waits_for_a_hidden_password_read`, `ctrl_c_during_a_password_read_waits_for_the_read_then_quits` (the Ctrl-C tests were seen failing first as compile errors). Real-terminal behaviour is on the human list (item reworded).

Ctrl-C at the password prompt needs Enter to take effect (a second Ctrl-C is deferred too). A tiny window exists between two `ctrl_c()` registrations in the forwarder where a SIGINT could be missed.

### Flaky `unread_count_reaches_two` (human-approved)
- Root cause (test race, not a core bug): the room list syncs with `timeline_limit` 1 and `num_unread_messages` is computed client-side from the timeline events the core receives. The test sent both messages right after joining, so if the core's sync only saw the room afterwards (slow CI), it got just the latest event and the count stayed at 1 forever. Reproduced deterministically by sending both messages before the core logs in (count stays 1 for 5 s+), and under `taskset -c 0,1` with CPU hogs (original test failed at `room_list.rs:51`).
- Fix: the test now waits for the room to appear, then sends "first" and waits for unread >= 1, then "second" and waits for unread >= 2. No timeout or sleep change.
