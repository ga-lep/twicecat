- Found by test: dropping a parsed tree of a few thousand nested elements overflows the stack (recursive `Drop` in ruma-html; reproduced at 6,000 `<div>` in a debug test thread, 2 MB stack), and an event can carry about 13,000 open tags. `from_html` therefore counts start-tag candidates (`<` followed by an ASCII letter) before parsing (`too_many_tags`, `MAX_TAGS` = 4,000) and uses the plain body above that. Security follow-up: the first guard mirrored the tokenizer (counting `</` as a close) and was bypassed by `<b></>` (ignored by html5ever), `</ x>` and `<!--</-->` (bogus comments), which parsed 10,900 levels deep. The count does not depend on tokenizer behaviour: a tree cannot be deeper than its element count, and every element needs such a candidate. It over-counts closed, void and commented tags (safe side). Why 4,000: 6,000 nested elements overflowed a 2 MB debug thread (smallest stack and largest frames we run on, tokio workers default to 2 MB), so 4,000 keeps a margin of 1.5x; the test parses exactly 4,000 nested `div`, `b`, `blockquote` and `ul`/`li` in a debug test thread. Normal messages are far below it (the 2,000-inline cap alone needs about 3,000 tags). Tests: `<b></>`, `</ x>`, `<!--</-->`, 5,000 `<div>`, and the max-depth case.
- Security follow-ups (linkifier and links): trailing-`)` stripping was quadratic (each strip rescanned the token; a 65,000-`)` token took 9 s in release, 39.5 s in debug). Parens are now counted once and updated while stripping, and tokens longer than `MAX_URL_BYTES` + 64 (`MAX_TOKEN_MARGIN`) are skipped, since they cannot be links. Regression test `linkify_trailing_parentheses_is_linear` (65,000 `)`, under 1 s). `mailto:` links keep only `subject`, `body`, `cc` and `bcc` (case-insensitive) in the query, so `?attach=/path` is dropped (`keep_safe_mailto_query`; the query is re-encoded, so `@` becomes `%40`).
- Not fixable in the core (spoofing): link and mention labels can differ from their targets (`<a href="https://evil.example">https://bank.example</a>`, a pill labelled with another user's name). Task 10 must show the real URL (or the real user/room ID) before opening a link or acting on a pill, and not rely on the label. Also on the Phase 3 human checkpoint.
- Choices the plan left open: the paragraph cap is 1,000 (`MAX_BLOCKS`); the text cap yields at most 16,385 chars (16,384 plus the ellipsis); a spoiler span flattens block elements inside it; `table` cells are joined by two spaces per row; the linkifier keeps `)` when balanced (Wikipedia-style URLs) and trims leading `( < ' "`.

## Phase 3 / Task 5 notes
- New private module `crates/core/src/outgoing.rs` (`outgoing_content`, Q10). Mention labels are linked at their first free occurrence (ranges never overlap; a label inside another mention's range is skipped), the label is backslash-escaped (all ASCII punctuation) and the user ID percent-encoded (`@alice:localhost` gives `%40alice%3Alocalhost`, accepted by Synapse and our mapper). `body` is the text as typed; `m.mentions` lists only users whose label was found. Text, notice and emote go through `*_markdown`.
- Raw HTML (Task 1 security note): ruma's `parse_markdown` is private and passes `Html`/`InlineHtml` through, so the formatted body is sanitized after the fact with ruma-html's `SanitizerConfig::strict()` plus `remove_elements(["img", "script", "style"])` (those go with their content; other unknown tags are dropped and their text kept). It runs on every formatted body, because markdown itself makes `[x](javascript:alert(1))`, `data:` links and remote `![](url)` images (strict allows `href` schemes http, https, ftp, mailto, magnet, matrix and `img` `src` mxc only, and the depth is capped at 100). Before parsing, the generated HTML (not the source: markdown nests with `>` or list markers and no `<`) is counted for start tags (`<` plus a letter); above `MAX_TAGS` = 1,500 the message is sent as plain text with no `formatted_body` (also for the line-break fallback), so the tree parsed here and, later, by the Task 4 mapper (`MAX_TAGS` 4,000 there; 6,000 nested elements overflowed a 2 MB debug thread) stays far from the stack limit. Tests: `<img src=x onerror=alert(1)>`, `<script>`, `<p onclick>`, `<iframe>`, `javascript:` links (unit), and an integration test that reads the event from the server and checks `formatted_body` holds `<strong>b</strong>` and no `<img`, `<script` or `onerror`. Code spans keep their `<` as `&lt;` (tested). Added: the three markdown-only leaks, `<a title href=javascript:>`, `>` x 50,000 with and without a leading `<b>x</b>`, `- ` x 50,000, 5,000 `![](u)` (all on a 2 MiB debug thread: no crash, no `formatted_body`; pulldown-cmark itself caps `>` nesting at 100, the guard does not depend on that), 1,490 raw `<div>` kept and mapped by `from_html` on a 2 MiB thread, and 1,510 lines sent without formatting.

- Reset race fix (phase4.5 follow-up). Cause: the sync service sends the SDK's `/keys/query` next to every sync request (matrix-sdk-0.19.1 `sliding_sync/mod.rs:633`, `send_outgoing_requests` in a task per request; `encryption/mod.rs:857-889`, `send_outgoing_request` -> `keys_query` :566). `OlmMachine::bootstrap_cross_signing(reset)` saves the new private keys at once (matrix-sdk-crypto-0.19.1 `machine/mod.rs:808-835`) and the public ones reach the server later (`encryption/mod.rs:1593-1640`; for OAuth only after approval, up to 2 minutes). A query that was answered with the old identity and is processed after that goes through `check_private_identity` / `clear_if_differs` (`identities/manager.rs:462-470`, `olm/signing/mod.rs:351`) and drops the new keys for good. The own-user query is dirty after every sync that reports our own device-list change (login, key and signature uploads, enabling recovery), which is why it hit right after login and right after enabling recovery. The `keys_gate` cannot cover the SDK's own requests. Fix: `SyncPause` (`crates/core/src/sync.rs`) stops the `SyncService` for the whole `bootstrap` and `reset` (also the OAuth wait) and starts it again afterwards. `SyncService::stop` returns only after the supervisor has ended both sync tasks (matrix-sdk-ui-0.19.1 `sync_service.rs:657-668`, `shutdown` :318-331, supervisor loop :246-330), so no query is in flight when the new keys are made. The supervisor's `restart` takes the pause gate (`ServiceControl` in `engine.rs`), so a sync failure during the pause cannot bring the sync back early; `Active::stop_tasks` aborts the security tasks first, which drops the gate (no deadlock on logout). Before the pause the SDK's one-shot setup task is awaited (`wait_for_e2ee_initialization_tasks`, `encryption/mod.rs:2176`; with `auto_enable_cross_signing` it bootstraps and queries keys itself). The own-identity query of `finish` now runs while still paused, so a failed or cancelled reset drops its never-uploaded keys at a safe time. After a reset that reported success the core checks `cross_signing_status().is_complete()` and else answers `ActionFailed` with a fixed message (`reset_complete`; this also catches another device changing the identity meanwhile). `reset_end`'s upload check (cancelled OAuth reset) now needs complete private keys as well as server master == local master, so a sync-overwritten public identity cannot make a cancelled reset look like a success. `keys_gate` and the identity permit are unchanged. Rejected: exporting and re-importing the private keys (the clear can happen before the export, inside `reset_identity`) and redoing the reset (new UIA or OAuth approval, and it could replace an identity another device changed). - Room selection: `RoomListChanged` deselects (and drops the draft and timeline) only while the query is the default; with a search or a non-default tab the open room and its draft stay even if the filtered list lacks the room (including a `Clear`). Logout, expiry and the default query still deselect. Tests cover search, tab, default query, return to the default query, logout and expiry.
- `pending_cancel` is cleared on `NoSession`, `LoggedOut` and `SessionExpired` (`back_to_login`). Test: `a_pending_cancel_is_forgotten_when_the_session_state_changes`.
- Checks: fmt, clippy (`--all-features --locked -D warnings`), `cargo test --workspace --locked`, `check-app-deps.sh`, `check-core-api.sh`, `cargo deny check`, shellcheck, and the ignored run against the local Synapse (`create-test-users.sh` with the new guard and prune, then `-p tessera-core -p tessera-app -- --ignored --skip keyring`; all suites ok, no flaky run) all pass; the keyring test was not run; `docker compose stop` afterwards.
- Open issues left by this step:
  1. `is_combining_mark` is still a hand-written list, not the full Unicode Mn/Me table: marks of scripts not listed (Devanagari, Bengali, Tamil, Thai tone marks outside the range and so on) still count as base characters and reset the counter, so a run alternating a listed and an unlisted mark is not capped. Closing this needs the full table (a generated range table or a crate such as `unicode-normalization`/`unicode-segmentation`, which needs approval as an app dependency). Output length is still bounded by the 256/4096 character caps.
  2. Selection keeps a hidden room only while a non-default query is active; a stale list update for the old query arriving just after the user returned to the default query can still drop the open room (the following `Reset` shows it again, but the draft is gone).
  3. The subdivision-flag rule keeps up to 8 invisible tag characters after any U+1F3F4, a small amount of smuggling room for a hostile sender, not checked against the valid flag tag list.
  4. A selector and a joiner each survive once per base, so a hostile string can carry two invisible characters per visible character within the length caps.
